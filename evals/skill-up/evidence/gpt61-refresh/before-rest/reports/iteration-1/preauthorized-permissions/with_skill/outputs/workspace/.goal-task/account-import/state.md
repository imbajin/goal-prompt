## 执行循环与验证

- 先核查既有实现、标准库、原生能力和已安装依赖；修改严格对应账户导入。依赖只做必要调整并同步锁文件；避免无关重构，不覆盖他人改动。
- 按共同模块、根因或验证面组织小批次；冻结批次后做受影响测试和定向检查；阶段边界及最终集成 diff 冻结后运行仓库要求的较广检查。基线变化后更新证据，不复用无效的旧 SHA 验证结果。
- 可先为用户要求的 push/PR 流程创建明确披露待测试、待审查风险的 checkpoint commit 和草稿 PR，再运行完整测试并处理 review；checkpoint 不代表门槛通过。主要里程碑通过适用验证与独立审查后及时提交；最终推送并核查 PR head 与全部证据一致。不得以空提交充当进展，不默认 merge 或改写远端历史。
- 3 名 reviewer 各自独立；较大变更均先扫全局风险，再分别聚焦正确性/测试、设计/边界、安全/可维护性；小变更三人各自审完整 diff。实现者自查不替代 reviewer，修复后必须复审。默认最多 3 轮修复/复审，仍失败则记录并延期受影响项，不放行门槛。
- 能节省时间的独立子任务可并行，明确独占文件和责任；锁文件、schema、生成文件等共用写点由一人负责，主执行者负责集成。告知 worker 非独占仓库，不回退他人改动。输入未齐的任务不提前写入，集成后重跑交界检查。
- 等待浏览器/会话时继续仓库分析、导入逻辑、边界校验、测试及依赖检查；等待 CI 时继续失败分析、审查、PR 说明及脱敏验收准备；等待 reviewer 时继续测试和浏览器验证；等待远端时完成本地实现、验证、提交和交付材料。仅推进有实际价值且不冲突的任务，不制造忙碌。
- 每项默认最多尝试 3 次；保留错误、证据、已尝试恢复及依赖，然后标记 waiting/deferred/needs input，将其及依赖项排在可独立工作之后。阶段边界或解除条件改变时重新检查，不盲目重试，不削弱断言或跳过必需检查。
- reviewer 不可用时，尽早报告缺失能力，完成无需 review 的工作，将该项保留 needs input；不得用自审替代或立即把整体设为 blocked。
