# 场景指南

只读取与用户任务匹配的部分。这里记录的是对 `SKILL.zh-CN.md` 两阶段流程的补充，不是完整 prompt 模板。调查阶段使用这些要点完善待确认摘要；用户确认前不要生成最终 `/goal`。

## 重构

- 写清目标状态，以及必须保持稳定的 API 或外部行为。
- 确认前检查调用方、测试和公开契约，不能只凭目录名猜测重构边界。
- 范围限定在受影响子系统，并明确相邻排除项。
- 使用仓库已有的定向测试，加上最小且相关的宽范围门槛。
- 按任务规模和风险使用对应审阅数量：快速模式的小型低风险变更使用 1 个 reviewer，深度模式或重大变更使用 3 个。
- 未获批准的 API、Schema 或依赖变更先延后；完成其他范围内工作后，只有它确实影响全部剩余任务时才询问。

## 功能开发

- 优先复用已有 SPEC、设计和任务文件。
- 起草目标摘要前，比较期望行为、当前实现和已有测试。
- 深度模式创建 `state.md`；只有 TODO 体量大或存在稳定设计决策时，才拆出 `todo.md` 或 `design.md`。
- 顶层完成门槛必须对应可观察行为和仓库验证器。
- 行为变更的重大里程碑使用 3 个独立 reviewer，并在修复后复审。

## 批处理

- 写清集合来源，已知时给出准确数量。
- 确认集合是否可能动态变化。
- 每项细节放在 `todo.md`、`state.md` 或正式证据产物中，不写入 `/goal`。
- 只有清单较大或频繁变化时才创建独立 `todo.md`。
- 固定分母使用准确百分比；成员会变化时使用基于证据的粗略估计并标注“估计”。
- 说明条目消失、变化或无法复现时如何处理。
- 按共享模块、根因或验证面形成批次，不使用任意固定条数。

## 调研

- 写清调研要支持的决定和证据标准。
- 确认问题前，先检查可访问的一手来源；区分“缺少证据”和“缺少用户偏好”。
- 适当时把可写范围限制为指定报告文件。
- 引用真实文件、行号、命令输出或一手来源。
- 纯文档、只读调研或分析默认使用 1 个独立 reviewer。
- 先穷尽可访问证据和独立调研路径，再因强制证据不可访问或权威来源冲突而请求输入。

## 审计

- 写清权威对照来源和审计单元。
- 确认边界前，同时检查声明的基线和有代表性的实现切片。
- 区分观察证据与推断，并标记只能通过运行时回答的问题。
- 报告包含精简发现摘要、证据和可执行优先级。
- 详细审计行写入正式报告，不写入 `/goal`。
- 除非用户明确扩展到修复，否则保持只读；默认 1 个独立 reviewer。

## 门禁审查

这里指目标本身就是判断分支、PR 或改动是否就绪，不等同于实现任务结束后的独立 reviewer。

- 保持只读，不实现、不 push、不 merge、不 rebase。
- 审查真实最终 diff 和相关验证证据。
- 第一阶段确认目标修订、已有检查和评论。
- 发现应包含严重度、准确位置、证据和建议。
- 使用小而明确的结论集合，例如 `ready`、`needs work`、`blocked`。
- 修订发生变化时重新刷新；某项验证暂不可用时先继续其他审查工作。

## 自定义

- 只有其他场景都不适用时才选择。
- 重点澄清结果、证据和真正影响全部剩余工作的停止条件。
- 只加入有用户要求或仓库证据支持的约束。
- 根据任务复杂度和行为风险选择文件、进度与 reviewer 规则，不机械堆叠。
