# 长任务执行循环

只对需要远程 CI、慢速验证、外部环境、跨阶段或跨配额恢复的深度任务使用。完整规则放入 `.goal-task/<task-slug>/state.md`，最终 `/goal` 只保留入口和完成门槛。

## 初始化与状态归属

深度模式固定创建非空 `state.md`，记录：

- 当前基线修订与环境；
- 活跃事实索引和权威层级；
- 阶段、各完成门槛的当前状态与当前优先级；
- 验证和 reviewer 证据；
- waiting / deferred 事项汇总、恢复状态与依赖；
- 下一个核心动作和恢复入口；
- 适用的进度、重试、审阅、提交和经验规则。

只在职责确实独立时拆分：

- 大量或频繁变化的工作项进入 `todo.md`；
- 已确认的长期设计决定进入 `design.md`；
- 有证据支撑的可复用经验进入 `lessons.md`；

存在 `todo.md` 时，事项级状态及 waiting / deferred 标记只在该文件维护；`state.md` 只保留数量、依赖摘要和链接，避免双写。

无法提前完成的一次性准备动作直接写入 `state.md` 的“初始化待办”，包含动作、授权状态、完成条件和当前结果。完成后删除操作步骤，只保留仍会影响后续执行的环境结果或约束。

初始化时审计一次当前修订、现有材料和执行权限。后续只在范围、基线、关键设计或环境发生实质变化时增量刷新，不重复读取全部历史初始化材料。

## 权限与环境预检

第一轮只验证本任务可能使用的写入、命令、网络、子 Agent、Git、连接器和唤醒能力。发现可能影响后续阶段的权限缺口时，立即高风险提示：

- 缺少的准确能力；
- 可能受影响的任务或门槛；
- 建议用户如何调整。

不要自行扩大权限。权限或授权缺口记为 `needs input`，继续所有不依赖它的工作，不自动设置整个 goal 为 `blocked`。

worktree、分支创建或切换、依赖安装、配置修改、破坏性动作和远端变更，必须在用户确认中列出准确目标与影响。同一次确认已经明确批准时，不再重复询问。

## 批次与验证节奏

把共享页面、模块、根因或验证面的低风险改动组成批次。批次冻结后运行受影响测试和定向 lint / check；完整构建、发布包检查、宽范围浏览器矩阵和聚合审阅放在阶段边界或最终 diff 冻结后。

当风险增加、公开契约改变或失败无法安全定位时，将项目从批次中拆出。不要为了追求进度而削弱断言、跳过强制检查、忽略退出码或伪造绿色结果。

## 等待期间的并行工作

构建、测试、CI、下载或环境启动预计超过两分钟时，如果存在不冲突的有效工作，就开启独立路径，例如：

- 下一模块的只读摸底；
- 文件所有权不重叠的实现；
- 证据和状态维护；
- 失败日志分析；
- 验收准备。

不要制造忙碌。并发实现者不能修改同一文件；只有隔离能实质降低冲突或偏差时才使用 worktree，而且必须已获授权。

## 重试、延后与停止

除非用户明确指定其他规则，单个事项最多尝试三次。仍失败时：

1. 记录错误、证据、已尝试恢复方式和依赖；
2. 标记为 waiting 或 deferred；
3. 把它及其依赖项排到独立工作之后；
4. 继续当前价值最高的范围内任务；
5. 在阶段边界或解除条件变化时重新检查。

瞬时网络故障、CI 排队、第一次失败、可修复测试错误、API 调整、配额等待和可选依赖缺失都不是整体终止条件。

资源受限时，依次考虑降低并发、减小批次、调整验证节奏和使用已授权的替代资源。资源限制仍无法解决时，可以延后当前事项，但不能豁免其完成门槛。

只有用户明确声明了 block 规则，或所有有意义的剩余任务在有限恢复、已授权替代方案、拆分、重排和完成全部独立工作后，仍共同依赖同一个逻辑冲突、安全边界或已验证的强制外部依赖，才把整个 goal 设为 `blocked`。

## 循环与里程碑进度

每个有实质产出的执行循环，以及重大里程碑审阅或提交跨越独立循环时，向用户输出：

```text
进度 [██████░░░░] 60%（3/5 门槛）
本轮：<完成事项与关键证据>；剩余：<主要未完成事项>。
下一步：<一个最核心动作>。
```

百分比基于范围内里程碑、交付物和完成门槛。分母固定时使用准确值；分母不稳定时使用粗粒度证据估计并标注“估计”。全部适用门槛通过前不得报告 `100%`。同一循环内完成的审阅和提交合并到一份小结。

## 独立审阅

### 行为变更

最终重大里程碑固定使用 3 个独立、只读 reviewer；深度任务的中间重大里程碑也使用同一规则。

- 改动较多：都先做全局风险扫描，再分别侧重正确性与测试、设计与边界、安全与可维护性。
- 改动较少：3 个 reviewer 各自独立完整审阅。
- 修复后复审受影响改动。
- 默认最多 3 轮修复—复审；仍未通过时记录并延后受影响事项，不能声称完成。

### 纯文档与调研

纯文档、只读调研和分析默认使用 1 个独立 reviewer。用户或仓库规则可以提高数量。

无法获得规定 reviewer 时，提前高风险提示，完成所有不依赖审阅的工作后保持 `needs input`。不要由实现者自审替代，也不要因此自动把整个 goal 设为 `blocked`。

## 里程碑提交

重大里程碑产生仓库内持久化改动时，完成适用验证和审阅后及时创建本地 commit。没有文件改动的只读任务不创建空 commit。默认不 push。

高严重度问题、测试失败或未通过门槛应先修复。如果当前改动是后续任务必需的基线，可以记录风险与未通过项后提交中间 checkpoint，但它不代表审阅通过，也不完成对应门槛。

## 配额与会话连续性

配额敏感工作开始前，确认原生 checkpoint、非阻塞等待 / 唤醒和同一 goal 的恢复方式。配额耗尽时：

1. 更新 `state.md`，记录状态、证据、已完成工作、当前等待或失败、验证结果、未提交改动、重置时间和下一步；
2. 可用时从权威界面核验重置时间；
3. 使用非阻塞等待，在重置后恢复同一 goal；
4. 不创建重复 goal，不把配额暂停当作失败，不忙轮询，也不保持长时间前台 sleep。

只有原生恢复不足时才创建本地辅助工具，并要求支持 dry-run、明确时区、幂等 checkpoint 和经验证的唤醒方式；不要编造产品恢复命令。
