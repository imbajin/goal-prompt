# 设计来源与取舍

本项目融合了两个参考方案的思路，但没有逐字复制：

- OpenAI `define-goal`：<https://github.com/openai/skills/blob/main/skills/.curated/define-goal/SKILL.md>
- `win4r/goal-prompt-builder`：<https://github.com/win4r/goal-prompt-builder>

## 保留

来自 OpenAI `define-goal`：

- 用具体结果代替活动描述；
- 明确验证证据和诚实的二元或定量阈值；
- 限定范围，并写清真正需要停止询问的条件；
- 只有缺失信息会改变目标时才提问；
- prompt builder 不执行 goal。

来自 `goal-prompt-builder`：

- 生成可以直接复制的 `/goal`；
- 以结果、范围、约束、并列完成门槛和例外停止条件为核心；
- 调查仓库上下文并按任务场景补充规则；
- 生成后简要解释关键取舍。

## 主要修改

- 从单阶段生成改为“调查与确认 → 初始化与生成”两阶段。
- 自动推荐快速或深度模式，但最终由用户确认。
- 深度模式可以在确认后创建已批准的 `.goal-task/<slug>/` Markdown 文件。
- 一次性环境准备不进入长期 prompt；无法提前完成时，暂记在 `state.md` 的“初始化待办”，完成后简化或移除。
- 完成门槛和停止条件按真实需求确定，不追求固定数量。
- 质量状态只使用 `ready` 或 `needs confirmation`，不用伪精确评分。
- 命令、路径和限制必须来自仓库或用户证据。
- token 预算只在用户明确要求时加入。

## 初始化文件设计

文件选择由职责驱动，不按任务复杂度机械凑数：

- 快速模式默认不创建文件；需要恢复连续性时才使用 `state.md`。
- 深度模式固定创建非空 `state.md`。
- 大量或频繁变化的工作项才拆到 `todo.md`。
- 需要稳定权威的确认决策才使用 `design.md`。
- 有证据支撑的可复用经验才创建 `lessons.md`。

不创建 `goal.md`，也不再机械创建 `progress.md`、`blockers.md` 或 `decisions.md`。大型报告和正式 SPEC 可以作为任务产物存在，但不属于默认初始化文件。

`state.md` 是活跃状态和索引，不覆盖权威 SPEC 或设计。任务材料内部遵循：

```text
用户最新确认 > 权威 SPEC / design > Issue / todo > state
```

## 持续执行与状态

- 单项普通失败默认最多重试三次，然后记录并延后，继续独立工作。
- 权限或授权缺口标记为 `needs input`，不自动阻塞整个 goal。
- 资源限制优先通过降低并发、缩小批次或调整资源使用处理。
- 延后事项仍保留完成门槛，不能因此报告 `100%`。
- 整体 `blocked` 只用于用户明确规则，或所有剩余工作都受同一逻辑冲突、安全边界或已验证强制外部依赖限制的例外情况。

## 进度、审阅与提交

- 每个有实质产出的循环，以及重大里程碑审阅或提交跨越独立循环时，输出三行进度小结；同一循环内的审阅与提交合并汇报。
- 百分比来自范围内里程碑、交付物和完成门槛；分母不稳定时标注“估计”。
- 行为变更的最终重大里程碑固定使用 3 个独立 reviewer；深度任务的中间重大里程碑同样适用。
- 纯文档、只读调研或分析默认使用 1 个独立 reviewer。
- 默认最多 3 轮修复—复审，未通过项记录并延后，不能冒充完成。
- 产生仓库内持久化改动时，在适用验证和审阅通过后及时创建本地 commit；只读任务不创建空 commit，默认不 push。
- 必需的下游基线可以带着明确风险提交 checkpoint，但不代表审阅通过。

## 经验学习

深度模式默认在每个有效循环后做简短归总，但只有真实、可复用、证据充分的经验才写入 `lessons.md`。快速模式只在用户要求或发生明确失败时启用。

经验可以成为仓库规则、全局规则或 Memory 的候选，但不能自动提升。修改 AGENTS 指令或 Memory 需要用户另行明确授权。

这些取舍主要解决：目标未经调查就定稿、初始化工作反复消耗上下文、sidecar 文件过多且职责重叠、普通失败过早阻塞、等待期间停止推进、缺少稳定进度反馈、独立审阅不足，以及跨轮经验无法复用。
